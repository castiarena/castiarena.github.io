## `<html>` wiring for U1

```tsx
import { geistSans, geistMono } from '@/components/shared/fonts'

<html
  lang="en"
  className={`${geistSans.variable} ${geistMono.variable}`}
  suppressHydrationWarning
>
```

Dark is the default theme, so wire `next-themes` (already installed) as
`<ThemeProvider attribute="class" defaultTheme="dark" enableSystem={false} disableTransitionOnChange>`
inside `<body>`. `suppressHydrationWarning` on `<html>` is required because next-themes sets the
`class` attribute (and therefore which of `:root`/`.dark` applies) after hydration.

## Decisions

- **Dropped the shadcn convention tokens** (`--primary`, `--secondary`, `--accent`, `--popover`,
  `--card-foreground`, etc.) that the wave-1 file had. `01-design-tokens.md` §9 doesn't define them,
  and `00-README.md` says explicitly that F2 writes its primitives against the new token names
  (`bg-card`, `text-brand`, …) from day one, with F1 only making those names resolve. Several
  existing primitives (`button`, `card`, `dialog`, `field`, `navigation-menu`, `sheet`, `sonner`)
  still reference the dropped tokens and will render unstyled until F2's restyle lands — expected
  fallout of running foundations agents in parallel, not a regression to fix here.
- **Kept `@import 'shadcn/tailwind.css'`** (STATE.md item 14). It's not in the 01 §skeleton, but
  removing it breaks the `data-open`/`data-closed`/`data-checked`/`data-unchecked`/`data-active`
  custom variants used by `field`, `sheet`, `scroll-area`, `navigation-menu`, `toggle-group`,
  `tooltip`, `dialog` and `separator`, plus the accordion open/close keyframes. F2 can drop it once
  none of its restyled primitives depend on those variants.
- **Added `--color-brand-foreground: var(--brand-foreground)`** to `@theme inline`, one line beyond
  the literal 01 §9 snippet. Without it, `text-brand-foreground`/`bg-brand-foreground` don't resolve
  as Tailwind utilities, and the standard "solid brand fill + contrasting text" button pattern
  (`bg-brand text-brand-foreground`) can't be written. Recorded in `01-design-tokens.md` §9 too.
- **Darkened `--brand-foreground` for the dark theme only** (task 10). The spec value
  `oklch(0.99 0 0)` (white) only clears 3.45:1 against the dark theme's `--brand`
  (`oklch(0.63 0.19 256)`, marked "from design" — locked). `--brand-foreground` is _not_ marked
  "from design", so it's the token that moves: darkened (lightness only, chroma stays 0) to
  `oklch(0.15 0 0)`, which clears 5.54:1. No single grayscale value clears 4.5:1 against both
  themes' `--brand` at once (dark `--brand` is bright enough that white text fails; light `--brand`
  is dark enough that even pure black only reaches 4.42:1) — confirmed by sweeping L from 0 to 1 in
  both themes — so the token had to become theme-specific either way. Light theme keeps the spec's
  `oklch(0.99 0 0)` (4.61:1, already passing). Documented in `01-design-tokens.md` §1/§2.
- **`container-page`'s responsive rule is nested inside the `@utility` body, not written as a
  second top-level `@media { @utility … }` block.** The literal code in 01 §4 (`@media (width >=
40rem) { @utility container-page { … } }`) doesn't compile on the installed Tailwind 4.3.3
  (`` `@utility` cannot be nested ``). Functionally identical output; `@media` nested _inside_ an
  `@utility` body (already used elsewhere in this file, e.g. `bg-hero-mesh`'s reduced-motion rule)
  is the supported direction.
- **`--destructive` and `--warning` use the same value in both themes.** 01 §2's light table omits
  them; since they're saturated accent hues (like `--brand-2`/`--brand-3`/`--brand-4`, which are
  also explicitly "identical in both themes"), not lightness-scaled neutrals, I extended that rule
  to them rather than inventing new light-theme values. Not covered by the §10 contrast table, so
  no test enforces it — flagging for F2/V1 in case `--destructive` text needs its own light-theme
  check once it's used for real error copy.
- **No `--radius-full` token.** Tailwind's built-in `rounded-full` utility already emits `9999px`
  without a theme variable; adding one would just be dead weight.
- **Skipped the token reference page** (task 9). `src/app/styleguide/` was created by 1.1, not 0.1,
  and `00-STATE.md`/`00-README.md` both say F2 owns the style guide end to end — extending it here
  would collide with F2's rebuild.

## Gate fix — restored `.light` (trial-merge finding)

A trial-merge gate (`agent/F1` + `agent/F2` + `agent/F3`, built and screenshotted) found that my
01 §2 rewrite of `globals.css` dropped the `.light` class selector the wave-1 file had. `.light`
lets a subtree force the light palette inside a dark page — `/styleguide/`'s "Colour tokens"
section wraps its light-theme panel in `class="light …"` for exactly this reason. With `.light`
gone, that panel inherited the ambient dark tokens and rendered dark swatches under a "LIGHT
THEME" caption.

Fix: `:root { … }` is now `:root,\n.light { … }` (the light-theme token block, unchanged values,
now also applies to any element carrying `class="light"`), plus a `.light { color-scheme: light; }`
rule after `.dark`, mirroring the wave-1 file's structure exactly. No token values changed — only
the selector.

This broke `tests/unit/shared/contrast.test.ts`'s `readTokens(':root')` helper, which matched the
**first** rule whose selector was the literal string `:root` — with `.light` appended, the
selector became `:root,.light`, so the helper silently fell through to the _next_ `:root` rule in
the file (the reduced-motion override, `--dur-ui`/`--dur-reveal` only), and every other light-theme
token read back as `undefined`. Fixed `readTokens` to split each rule's selector on `,` and match
any member of the list, so `:root` still resolves to the first rule whose selector list _contains_
`:root` (the intended token block, not the later reduced-motion one). No test assertions or
expected values changed.

Verified interaction with `@custom-variant dark (&:is(.dark *))`: that variant only affects
`dark:`-prefixed Tailwind utilities: it has no bearing on the plain `:root`/`.dark`/`.light`
custom-property rules. Confirmed a `.light` subtree nested inside a `.dark` page wins, via
Playwright against a static `pnpm build` + `serve out` (port 4173 was occupied by the reviewer's
own trial-merge server from a different worktree, so `serve` was pointed at its fallback port
instead — same static output, same result): with `<html class="dark">` and the style guide's light
`ThemePanel` nested inside it, `getComputedStyle(.light).getPropertyValue('--background')` reads
the light value (`lab(100% 0 0)`), `.dark`'s sibling panel reads the dark value, and
`getComputedStyle(.light).colorScheme` reads `"light"` — confirming the escape hatch works with
dark as the default theme. (`scripts/shoot.mjs` is on `agent/F2`, not this branch, hence Playwright
instead of a screenshot.)

Full gate re-run, repo-wide (not scoped to files I own, per the gate note that the previous round
