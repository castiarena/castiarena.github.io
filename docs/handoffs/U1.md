## Decisions

- **`enableSystem` is `true`, not `false`.** F1's handoff suggested
  `enableSystem={false}` in its `<html>`-wiring snippet, but `02-component-specs.md`'s
  `ThemeToggle` spec explicitly cycles "light → dark → system", and my own mission's task 2 lists
  `enableSystem` as a bare flag (i.e. `true`) alongside `defaultTheme="dark"`. `enableSystem={true}`
  with `defaultTheme="dark"` gives both: dark is what a new visitor with no stored preference sees,
  and "system" stays a selectable third mode from the toggle. Confirmed `scripts/shoot.mjs` still
  works with this wiring — see the next bullet.
- **`scripts/shoot.mjs` theme switching still works, no CCR needed.** The harness writes
  `localStorage.theme` and toggles `.dark` on `<html>` via `addInitScript`, which Playwright
  guarantees runs before any of the page's own scripts — including next-themes' own anti-flash
  inline script in `<head>`, which reads `localStorage.getItem('theme')` (default storage key,
  unchanged) and applies the same class next-themes would apply itself (`classList.add('light'
| 'dark')`, mutually exclusive with the other). I verified this by rebuilding, re-shooting `/`,
  `/bio/` and `/404` at both viewports/themes, and confirming `shoot.mjs`'s own dark-vs-light
  background-colour assertion still passes (it throws if the two don't differ) — see the
  screenshots in this folder.
- **`/404` pathname detection catches the built `out/404.html` and direct `/404` visits, not every
  `notFound()`.** I confirmed by building, serving `out/`, and reading back a debug
  `usePathname()` value from the static 404 page: this Next.js version's not-found boundary
  resolves to the internal route `/_not-found` at build time, but once `serve` (and, per
  `04-visual-qa-protocol.md`, `pnpm start`/GitHub Pages' 404 fallback) serves it for the literal
  `/404` path, hydration reports `usePathname() === '/404'` — which is exactly the route
  `node scripts/shoot.mjs --route /404` and the acceptance criterion ("`out/404.html` shows the
  reduced header") both test. A `notFound()` thrown from _inside_ another route (e.g. an unknown
  project slug) keeps the browser's original requested URL after hydration, so it won't match
  `'/404'` and the header won't reduce there — a real, documented limitation of pathname-only
  detection on a fully static export, not something a prop-threading approach would have avoided
  either (the mission explicitly asked for `usePathname()`, not a prop).
- **The reference render (`08-not-found-desktop.png`) shows the full nav on `/404`; I built the
  reduced header instead.** The PNG contradicts both `03-page-specs.md`'s own prose ("Header on
  this page hides the nav links, only logo and Contact") and my mission's task 5, which are
  unambiguous and specific to this screen. `04-visual-qa-protocol.md` explicitly says reference
  renders aren't pixel-perfect targets and static mockups can't always encode state-dependent
  behaviour — I followed the written instructions and documented the divergence here rather than
  silently picking one. I also hid `ThemeToggle` on `/404` (mission says "only the logo and
  Contact button show"; the reference shows no toggle there either, so both sources agree on that
  part).
- **Added a "Home" nav item that isn't in `siteConfig.nav`.** Every reference screen
  (`03-home-desktop.png`, `08-not-found-desktop.png`, `10-mobile-menu.png`) shows `Home` as the
  first nav item, but the frozen `siteConfig.nav` only lists Bio/Projects/Experiments (Logo already
  links home). I render `[{ href: '/', label: 'Home' }, ...siteConfig.nav]` — this doesn't modify
  `site.ts` (frozen, not mine to touch) and task 9's test requirement ("nav renders every
  `siteConfig.nav` entry") still holds, it's just not the _only_ thing rendered. Nav order is
  therefore "Home Bio Projects Experiments" (siteConfig's order), not the reference's "Home Bio
  Experiments Projects" — `siteConfig.nav`'s order is the frozen contract, so it wins; noted here
  rather than reordered against the frozen array.
- **Real bug: the hamburger has to be an actual `SheetTrigger`, not a lookalike button that calls
  `setOpen(true)`.** I originally wired the mobile-menu button as a plain `Button` with
  `onClick={() => setMobileOpen(true)}`, next to a `Sheet` controlled by the same state. It opened
  fine, but closing (Esc or a nav click) dropped focus to `<body>` instead of the hamburger.
  Radix's `Dialog`'s default `onCloseAutoFocus` calls `context.triggerRef.current?.focus()` — it
  targets the specific element registered as `Dialog.Trigger`, not whatever
  `document.activeElement` happened to be before opening. With no real `Trigger` in the tree,
  `triggerRef.current` was `null` and focus fell through to the document body. Fixed by moving the
  hamburger into `MobileNav` itself as `<SheetTrigger asChild><Button ...>` (`SiteHeader` no
  longer renders a duplicate button) — confirmed with a Playwright script: focus now lands back on
  the `aria-label="Open menu"` button after Esc, both on click-away and on Esc close.
- **Real bug: `isNavActive` needs to special-case `href === '/'`.** My first draft of the active
  check in `MobileNav` was `pathname === href || pathname.startsWith(href)`, inlined separately
  from `SiteHeader`'s (correct) version. Since `href` for "Home" is `'/'`, `pathname.startsWith('/')`
  is true for _every_ absolute path, so Home was marked active on every route in the sheet. Fixed
  by extracting both call sites to a shared `isNavActive(pathname, href)` in `is-nav-active.ts`,
  which only treats a non-root `href` as a prefix match; caught by
  `tests/unit/layout/mobile-nav.test.tsx`'s "marking the active one" test.
- **Real bug: the close-on-navigation effect in `MobileNav` fired on mount, not just on route
  change.** `useEffect(() => onOpenChange(false), [pathname])` runs on the component's first mount
  too (React doesn't skip the first invocation), so a sheet opened for the very first time would
  immediately call `onOpenChange(false)` on itself. Fixed with an `isFirstRender` ref that skips
  the effect's body on mount; `mobile-nav.test.tsx` asserts `onOpenChange` is _not_ called until a
  subsequent `pathname` prop change.
- **`focus-ring` utility bug caught via screenshot, not lint/typecheck/tests.** I initially added
  the `focus-ring` utility class (unconditionally) to `Logo`, `NavItem` and `MobileNav`'s links,
  assuming it was the project's way of drawing a visible-focus ring. It isn't gated behind
  `:focus-visible` — `globals.css`'s own base layer already applies `:focus-visible` globally to
  every element, and the `focus-ring` utility (per F1's comment on it) is for elements that "can't
  rely on `:focus-visible` alone," meant to be combined with a `focus-visible:` variant, not applied
  bare. Applying it bare drew a permanent blue outline box around the logo and every nav item at
  all times, visible in the first `home-1280-dark.png` shot. Removed it from all three files; none
  of the automated checks would have caught this since it's a purely visual regression — reinforces
  why the visual pass matters.
- **`viewport.themeColor` needs two literal OKLCH strings**, which the colour-literal grep in
  `04-visual-qa-protocol.md` §3 would otherwise flag. A `<meta name="theme-color">` value is read
  by the browser chrome outside the CSS cascade, so it cannot reference a `var(--background)`
  custom property — it has to be a literal string. `THEME_COLOR_LIGHT`/`THEME_COLOR_DARK` in
  `layout.tsx` mirror F1's `--background` value for each theme, with a comment explaining why (same
  approach F3 documents for its JS motion-duration constants). Confirmed this is the _only_ hit for
  `grep -rnE "#[0-9a-fA-F]{3,6}|rgb\(|oklch\(" src/components/layout src/app/layout.tsx`.
- **Footer's year is computed once at module evaluation** (`new Date().getFullYear()` inside the
  component body), not read from an env var or build-time constant file. For a static export this
  value is baked into the prerendered HTML at build time and only re-evaluated in the browser if
  the module re-runs (effectively never, absent a manual reload past a year boundary) — good enough
  for a footer credit line, not worth a dedicated build-time constant module for a value this minor.
- **`ContactDialog trigger={...}` used as instructed, not modified.** Per the orchestrator note, I
  don't own contact internals. The current stub wraps `trigger` in a bare `<a href="mailto:...">`,
  which means a `<button>` currently renders nested inside an `<a>` in my header/sheet — expected
  stub behaviour that U6 replaces with a real `Dialog`+`DialogTrigger asChild` composition; not
  something I can or should fix from here.

## Notes for downstream agents

- **V1 (final visual QA):** re-shoot `/`, `/bio/`, `/experiments/`, `/projects/`, `/projects/<slug>/`
  once U2–U6 land — my header/footer should already be correct everywhere, but worth confirming no
  page introduces its own duplicate header/skip-link/footer.
- **U2–U6:** the header is `sticky`, not `fixed` — you don't need any `pt-*`/`mt-*` compensation on
  your page's first section for it not to be covered. Anchor targets on your own page (e.g. Bio's
  `#about`/`#experience`/…) still need their own `scroll-mt-24` per `03-page-specs.md` — the sticky
  header doesn't provide that for you automatically, it just guarantees no overlap when there's no
  scroll offset in play.
- **U6 (contact form/dialog):** both `SiteHeader`'s desktop Contact button and `MobileNav`'s
  full-width one already call `<ContactDialog trigger={<Button ...>}>` — once you replace the stub
  with a real `Dialog`/`DialogTrigger asChild`, both call sites should keep working with no changes
  needed here.
- **Anyone touching `globals.css`'s `focus-ring` utility:** it is not `:focus-visible`-scoped by
  itself (see Decisions) — pair it with a `focus-visible:` variant, or don't add it to elements that
  already benefit from the global base-layer `:focus-visible` rule (any plain focusable element
  does, automatically, with no class needed).
