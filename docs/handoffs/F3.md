## Usage — nav underline helper

```tsx
import {
  NAV_UNDERLINE_LAYOUT_ID,
  navUnderlineTransition,
  useMotionAllowed,
} from '@/components/motion'
import * as m from 'motion/react-m'

function NavItem({ href, label, active }: { href: string; label: string; active: boolean }) {
  const allowed = useMotionAllowed()
  return (
    <Link href={href} aria-current={active ? 'page' : undefined}>
      {label}
      {active && (
        <m.span
          layoutId={allowed ? NAV_UNDERLINE_LAYOUT_ID : undefined}
          transition={navUnderlineTransition}
          className="absolute inset-x-0 top-full mt-1.5 h-0.5 bg-signature"
        />
      )}
    </Link>
  )
}
```

Gating `layoutId` itself (not just the transition) on `useMotionAllowed()` is what makes it reduced-motion safe: without a shared `layoutId`, Motion mounts and unmounts the underline per item with no `FLIP` animation between them, so it just snaps to the active item.

## Decisions

- **`MOTION_DURATION_UI` / `MOTION_DURATION_REVEAL` stay JS literals, not `getComputedStyle` reads of `--dur-ui` / `--dur-reveal`.** F1 adds those custom properties to `globals.css`, but a Motion `transition.duration` has to be a literal number of seconds at the point the animation is defined — including during SSR, where there's no `getComputedStyle` to call, and during the `variants`/`whileHover` objects defined at module scope, before any DOM exists to read a custom property from. Reading the token at runtime (e.g. in a `useEffect` that then re-triggers the animation) would add a layout-thrashing read and a race on first paint for a value that's a fixed design-budget constant, not something that's actually re-themed at runtime. Instead, the two are kept as two literals that must be kept equal by _convention_ (both trace to `01-design-tokens.md` §6: 200ms / 500ms / `cubic-bezier(0.22, 1, 0.36, 1)`), and `tests/unit/motion/budget.test.ts` pins the JS side's values and caps so a future edit that drifts either one fails a test instead of silently drifting from the token.
- **`navUnderlineTransition` lives in `shared.ts`, not a new file.** It's two primitives (a string and a transition object), not a component, and pairs directly with the `MOTION_DURATION_UI` / `MOTION_EASE` constants already there.
- **Renamed `MOTION_DURATION` → `MOTION_DURATION_UI` / `MOTION_DURATION_REVEAL`** rather than adding a second constant alongside the old name. Grepped `docs/` and `src/` first: nothing outside `src/components/motion/` referenced the old name, so this was a safe rename, and the split makes the UI-vs-reveal budget distinction explicit at every call site instead of implicit in a comment.

## Bundle measurements (re-check)

Same method as 1.3 (Next 16/Turbopack no longer prints first-load sizes): sum `gzip -9` of every `/_next/static/chunks/*.js` referenced by each exported route's HTML. Baseline measured by temporarily removing `MotionProvider` from `layout.tsx`, rebuilding, then restoring it and rebuilding again (`out/` is gitignored, so this doesn't touch anything committed).

| Route                                                            | Without `MotionProvider` | With `MotionProvider` (current) | Added                                                                                 |
| ---------------------------------------------------------------- | ------------------------ | ------------------------------- | ------------------------------------------------------------------------------------- |
| `/`, `/bio/`, `/experiments/`, `/projects/`, `/projects/<slug>/` | 173.5 KB                 | 186.8 KB                        | **+13.3 KB** ✅ (budget ≤ 35 KB)                                                      |
| `/motion-lab/` (every primitive)                                 | 198.3 KB*                | 203.3 KB                        | +5.0 KB over its own baseline; **+29.8 KB** ✅ vs the 173.5 KB provider-free baseline |

*`/motion-lab/` still imports the primitives directly with `MotionProvider` removed, so 198.3 KB already includes `Reveal`/`Stagger`/`HoverLift`/`CountUp`/`ParallaxLayer`/`ScrollProgress` — only the `LazyMotion`/`MotionConfig` wrapper itself is missing from that number, which is why its own delta (+5.0 KB) is smaller than the delta against the fully motion-free baseline (+29.8 KB, the number that's comparable to 1.3's original +29.1 KB).

Both deltas are within the 35 KB gzip budget. Absolute numbers are slightly higher than 1.3's (185.0 KB / 201.4 KB) because 1.1 (design system) has since merged into `next` and added primitives that `SiteHeader`/`SiteFooter`/`ContactDialog` stubs pull in — unrelated to motion.

Lazy chunks (unchanged from 1.3, not part of first load): `domAnimation` features ~17.3 KB, `animate()` for `CountUp` ~10.1 KB, both fetched only once a primitive is armed/used.
