## Decisions

- **`generate-covers.mjs`'s `main()` is now guarded** (`if (import.meta.url ===
\`file://${process.argv[1]}\`)`) instead of running unconditionally on import. The file's own
header comment says the sync test imports `getCoverGradientStops`from it; without the guard,
importing it for that test re-ran the whole file-writing script (with console output and a
20 KB-budget throw) as a side effect of`vitest`, on every test run.
- **No project currently has a `gallery` array** (`Project.gallery` is optional; `src/content/
projects.ts` doesn't set it — no real screenshots exist yet). Rather than hiding the whole Gallery
  section, `gallery-items.ts` falls back to 3 generated `CoverGradient` placeholders per project
  (same algorithm as the cover SVGs, different seeds), each with an explicit `TODO(agustin)` alt
  text. This keeps the section demonstrably working (and shootable/testable) instead of silently
  empty, consistent with how the cover placeholders themselves are handled. Once real gallery images
  exist, dropping them into content is enough — no component change needed.
- **Outcomes parsing**: `Project.outcomes` is unstructured CV prose (`string[]`), not `{value, unit,
label}`. `outcome-parsing.ts` regex-matches a leading number (`35% …`, `2x …`, `4+ …`) and renders
  those as `StatTile`; everything else — including every `TODO(agustin)` outcome in the current
  content — renders as the dashed, muted fallback card per `03-page-specs.md` §5. For a
  `TODO(agustin):` string specifically, the fallback card shows a mono `TODO(agustin)` eyebrow +
  the rest of the sentence as the body, matching screen 07 exactly.
- **`TODO(agustin)` copy renders in `--muted-foreground`** (task 7): title/problem/approach items
  that start with the literal `TODO(agustin)` prefix get `text-muted-foreground` wholesale (I did
  not strip the prefix — showing it as-is is the point, it's a placeholder marker for the site
  owner). The Outcomes dashed card is the one place that _does_ split eyebrow vs. body, because
  that's what screen 07 visually shows for that specific component.
- **Detail hero cover uses `object-contain`, not `object-cover`** (also the index rows' cover).
  The generated placeholder SVGs are natively 16:10 and bake the project title into the artwork
  (task 1). `03-page-specs.md` asks for a 4:3 cover on the index (desktop) and 21:9 on the detail
  hero (desktop) — both crop a 16:10 source under `object-cover`, and both crops land squarely on
  the baked-in title text (4:3 crops the sides where the text starts; 21:9 crops top/bottom where
  the text sits). `object-contain` + a `bg-muted` letterbox avoids cropping the title at the cost of
  a visible matte on non-16:10 boxes — visible in the screenshots, not a bug. `ProjectCard`,
  the gallery thumbnails and the mobile hero cover all use the _native_ 16:10 ratio, where `cover`
  and `contain` render identically, so I left those as `object-cover`.
- **`ParallaxLayer` + a `fill` `next/image` needed a specific wrapper structure to actually paint**
  (see the code comment in `projects-index.tsx`). Once `ParallaxLayer`'s motion wrapper gets its
  translate transform (after hydration), it becomes a CSS containing block for any absolutely
  positioned descendant — but that wrapper has no height of its own (only in-flow content sizes it),
  so a `size-full`/percentage-based child collapses to 0×0. Fixed by giving the child its own
  `aspect-*` (only needs a definite width, which a block box always has) instead of depending on the
  parent's height. This is a general gotcha for anyone using `ParallaxLayer` around a `fill` image —
  worth knowing for U2/U4 if either does the same.
- **CCR-U5-1 — `Button asChild` throws whenever `loading` is unset.** `ui/button.tsx`
  unconditionally renders `{loading ? <Icon/> : null}{children}`; when `asChild` is set, that's two
  children handed to Radix's `Slot`, which requires exactly one and throws `"Slot failed to slot
onto its children"` otherwise. Reproduced with a minimal `<Button asChild variant="outline"><a
href="...">Go</a></Button>` — fails every time `loading` isn't explicitly `true`. I don't own
  `ui/button.tsx`, so I worked around it locally in `project-hero.tsx`'s link buttons by using the
  exported `buttonVariants(...)` class list directly on a plain `<a>` instead of `<Button asChild>`.
  **F2**: the real fix is filtering falsy children before handing them to `Slot` (e.g. only render
  the icon element when `loading`, not `loading ? <Icon/> : null`), or gating the icon behind
  `Slottable`. Anyone else planning to use `Button asChild` — LinkedIn/GitHub buttons on Bio, "View
  projects" on Home, 404's buttons if any are links — will hit this until it's fixed.
- **axe-core (`@axe-core/playwright`) reports false-positive `color-contrast` violations against
  this codebase's OKLCH tokens.** Ad hoc `axe-check.mjs` (not committed — one-off verification, like
  F2's ad hoc Playwright scripts) found "violations" on `Badge`/`TagList` text and the lightbox's
  aria-live paragraph; in every case, directly reading `getComputedStyle` and computing the ratio
  with `culori`'s `wcagContrast` (the same tool `contrast.test.ts` uses) showed the real, rendered
  contrast was 7:1+ — comfortably passing. Axe appears to mis-sample when the browser reports colors
  as `lab(...)` (which Chromium does for OKLCH-declared colors) rather than `rgb(...)`. **Worth
  knowing for whichever agent wires up a real axe/Lighthouse check in wave 3+**: don't trust a
  `color-contrast` finding on this codebase at face value — verify the actual rendered colors first.
- **One real contrast finding, not a false positive**: the amber DRAFT badge (`--warning`, per
  `03-page-specs.md` §2) fails WCAG AA in the **light** theme — `text-warning` on white is 2.02:1,
  need 4.5:1. Verified directly (not through axe). `--warning: oklch(0.78 0.14 85)` is defined
  identically in both `:root`/`.light` and `.dark` in `globals.css` — unlike `--brand`, which
  01-design-tokens.md §2 explicitly darkens for light mode for exactly this reason, `--warning` never
  got the equivalent treatment, and `tests/unit/shared/contrast.test.ts`'s `TEXT_PAIRS` doesn't
  include `warning` so nothing caught it. I can't fix this myself (`globals.css` is F1's file, and
  the token vocabulary is frozen to what's listed in `01-design-tokens.md`). **F1**: please darken
  `--warning`'s lightness for `:root`/`.light` (mirroring the `--brand` treatment) and add
  `['warning', 'background']` to `contrast.test.ts`'s `TEXT_PAIRS` so it doesn't regress silently
  again. Low real-world exposure today since dark is the site default and the badge is
  non-production-only, but it's a real gap.
