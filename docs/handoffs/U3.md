## Decisions

- **Timeline gap note is computed, not hard-coded.** The CV has an undocumented Oct 2018 – Jan
  2020 gap (`docs/plan/assets/cv-content.md`, `src/content/experience.ts`'s own comment, and
  1.2's still-open "Needs human input" in `docs/handoffs/1.2.md`), but no content field carries a
  note string for it — `Experience` has no such property, and the mission says never to hard-code
  copy that content owns. `getTimelineGapNotes` sorts a copy of `experiences` chronologically and
  flags any pair of roles more than one month apart, rendering
  `TODO(agustin): confirm whether the <range> gap should be shown.` under the list — derived
  entirely from the two roles' own dates via `formatRange`, so it's a rendering behaviour I own,
  not invented content. **CCR against 1.2** (non-blocking): consider adding a real
  `timelineNotes`/`gap` field to content so this doesn't have to be inferred.
- **Achievement `StatTile` label is `achievement.title`, sentence-cased**, not `metric.label`.
  Comparing my first screenshot against `04-bio-desktop.png` side by side
  (`docs/handoffs/assets/U3/compare-bio-1280-dark.png`) showed the reference renders "Scalability
  enhancement", "Code review optimization", "Frontend optimization" — sentence case of `title`,
  not the shorter `metric.label` ("platform scalability" etc.), which doesn't match at all. The
  one exception is "Stakeholder satisfaction" vs. content's `title` "Stakeholder Satisfaction
  **Achievement**" — the reference mockup's copy is one word shorter than the shipped content;
  since content is 1.2's and I don't invent wording, I left `title` as-is and only fixed the case.
- **Dropped the CV caption's 90% opacity.** `03-page-specs.md` and my own prompt call for
  "PDF · 1.6 MB" at 90% opacity. Running `@axe-core/playwright` against the built page (see How to
  verify) found this drops `brand-foreground`/`brand` below 4.5:1 in the **light** theme
  specifically (dark theme's darkened `brand-foreground`, per F1's handoff, has more headroom and
  survives the 10% blend). Removed the opacity; the mono font + smaller size already read as a
  secondary caption without it. No serious/critical axe violations from my own code after this fix
  — the one remaining light-theme finding is a shared-component bug, see CCRs below.
- **CV/LinkedIn/GitHub buttons render as `<a className={buttonVariants(...)}>` instead of
  `<Button asChild>`.** See the CCR below — `asChild` is currently broken app-wide.

## Contract Change Requests

1. **`ui/button.tsx`'s `asChild` is broken whenever `loading` is left at its default `false`**
   (F2-owned, not fixed here per the loop protocol: "don't touch files you don't own"). Repro:
   `render(<Button asChild><a href="/x">Go</a></Button>)` throws `Error: Slot failed to slot onto
   its children. Expected a single React element child or Slottable.` Root cause:
   `<Comp>{loading ? <Loader2Icon .../> : null}{children}</Comp>` always passes Radix's `Slot` an
   array of **two** children (`null` + the single real child) whenever `loading` is falsy, and
   `@radix-ui/react-slot` only falls back to treating `children` as the slot target when
   `React.Children.count(children) === 1`— two children (even with one being `null`) fails that
   check and throws. This affects **every** non-loading `Button asChild` in the app, not just
   mine. Suggested fix (verified locally, not applied): render the icon and children as a single
   child, e.g. `{loading ? (<>{icon}{children}</>) : children}`, so `Comp` always receives exactly
   one element. Worked around locally in `bio-header.tsx` by rendering the anchors directly with
   the exported `buttonVariants(...)` instead of `<Button asChild>`, so no visual/behavioural
   change — just sidesteps `Slot`. **Every other agent using `Button asChild` (Home hero CTAs,
   ProjectCard, ExperimentCard's "Source" link, etc.) will hit this too** until F2 fixes it or
   they route around it the same way.
2. **`Badge variant="brand"` fails `color-contrast` in the light theme** (F2-owned `ui/badge.tsx`,
   not fixed here). `@axe-core/playwright` against `/bio/`'s Skills section (7 leadership badges,
   all using `variant="brand"`) reports a **serious** violation in light theme only (dark theme is
   clean). `tests/unit/shared/theme-tokens.test.ts` and `contrast.test.ts` don't catch this because
   neither checks the `brand` text-on-`brand/15%`-fill combination the badge variant actually
   uses. Not fixed here since `ui/badge.tsx` isn't mine; flagging so V1/F2 can adjust the variant's
   light-theme colours (e.g. a stronger fill or a darker text token) before the light theme is
   considered done anywhere it's used (Home's "Team Lead" tag, screen 02's leadership column, and
   here).
